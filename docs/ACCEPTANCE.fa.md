# تست پذیرش روی VPS و کلاینت واقعی

این راهنما مراحل باقی‌مانده برای تصمیم دربارهٔ استفادهٔ واقعی را مشخص می‌کند. تست‌های محلی جایگزین عملکرد روی شبکه، NAT، ISP و اپ موبایل نیستند.

## نصب در محیط آزمایشی

1. یک VPS آزمایشی Debian/Ubuntu انتخاب کنید. پورت پنل و IPv4 ICMP را در firewall باز کنید. سرور قدیمی روی همان IP را هم‌زمان اجرا نکنید.
2. `sudo bash install.sh` و گزینهٔ Install را اجرا کنید. اول HTTP عمومی را آزمایش کنید، سپس روی نصب جدا یا از گزینهٔ SSL، دامنه و Certbot را تست کنید.
3. با `sudo namedicmp` گزینهٔ ۶، Status and TCP/UDP diagnostics را ببینید. سرویس نباید در حلقهٔ restart باشد. `journalctl -u namedicmp -f` باید خطای permission/raw socket یا ذخیره‌سازی نشان ندهد. این نسخه شمارنده‌های ورودی و خروجی هر پروتکل، `outbound_errors` و `oversized_udp` را جدا نشان می‌دهد.
4. گزینهٔ Start/Stop، تغییر پورت، تغییر username/password و حذف با حفظ داده را بررسی کنید. نصب دوباره باید همان کاربران و شمارنده‌ها را نگه دارد.
5. برای HTTPS، پورت ۸۰ آزاد بماند. `certbot renew --cert-name namedicmp --dry-run` را اجرا کنید؛ برای آزمایش deploy hook از `--run-deploy-hooks` طبق نسخهٔ Certbot نصب‌شده استفاده کنید. درخواست HTTPS باید گواهی معتبر بگیرد و تمدید، نشست ICMP موجود را قطع نکند.

برای نصب قبلی 0.1، فایل ZIP جدید را باز کنید و `sudo bash install.sh` را **از پوشهٔ جدید** اجرا کنید؛ گزینهٔ **۲، Update** را بزنید. کلید و مصرف دو کاربر، رمز پنل، پورت و TLS را قبل/بعد مقایسه کنید. کاربران موجود باید «بدون رمزنگاری» بمانند. Update یک بار تونل‌ها را reconnect می‌کند و نسخهٔ پشتیبان مستقل می‌سازد. روی نصب متوقف نیز تست کنید؛ Update نباید سرویس را خودکار روشن کند.

## سازگاری

دو کاربر A و B با کلید متفاوت بسازید. در اپ مورد استفادهٔ واقعی نام و نسخهٔ دقیق را ثبت کنید. IP و کلید A باید اتصال بدهد؛ کلید اشتباه باید رد شود. سپس با B متصل شوید. برای نسخهٔ CLI رسمی:

```bash
sudo pingtunnel -type client -l 127.0.0.1:1080 \
  -s SERVER_IP -sock5 1 -key USER_KEY -tcp_gz 0
curl --proxy socks5h://127.0.0.1:1080 https://example.com/
```

تست curl بالا فقط TCP را ثابت می‌کند. ترافیک UDP مانند DNS معمولی و QUIC یا برنامهٔ UDP را جدا تست کنید. ابتدا خروجی Direct و کلاینت دارای UDP/VPN را انتخاب کنید. برای SOCKS محلی، نسخهٔ کلاینت و برنامهٔ مصرف‌کننده باید **UDP ASSOCIATE** داشته باشند؛ HTTP proxy، DNS-over-HTTPS و کلاینت TCP-only تست UDP نیستند.

هم‌زمان یک دانلود TCP را باز نگه دارید و UDP را به حداقل دو مقصد بفرستید. در یک ابزار آزمایشی UDP، payloadهای ۱۲۸، ۱۲۳۲ و ۴۰۹۶ بایت را مقایسه کنید؛ هیچ datagram نباید ناقص تحویل شود. بسته‌های بزرگ‌تر ممکن است به fragmentation IPv4 نیاز داشته باشند و شبکهٔ اپراتور می‌تواند آن‌ها را حذف کند. سقف فعلی ۸۱۹۲ بایت است، بدون افزونهٔ fragmentation یا retransmit برای UDP.

قبل و بعد گزینهٔ ۶ منو را ببینید. اگر TCP همان کاربر کار می‌کند ولی `udp_packets_in` زیاد نمی‌شود، مسیر ارسال UDP کلاینت/برنامه یا بسته‌های ICMP آن را بررسی کنید. اگر ورودی زیاد می‌شود ولی خروجی ندارد، لاگ/`outbound_errors`، مقصد و پشتیبانی UDP خروجی را بررسی کنید. SOCKS5 سرور هم باید UDP ASSOCIATE داشته باشد. HTTP CONNECT به‌صورت عمدی UDP را رد می‌کند و از مسیر مستقیم عبور نمی‌دهد.

برای رمزنگاری، پیش‌فرض **None** را تست کنید، سپس هر سه روش را جدا روی یک کاربر فعال کنید. کلاینت سازگار با رمزنگاری باید همان روش و کلید Base64 پنل را داشته باشد. مثال:

```bash
sudo pingtunnel -type client -l 127.0.0.1:1080 \
  -s SERVER_IP -sock5 1 -key USER_KEY -tcp_gz 0 \
  -encrypt aes256 -encrypt-key 'BASE64_KEY_FROM_PANEL'
```

برای AES-128 از `aes128` و برای ChaCha20 از `chacha20` استفاده کنید. TCP و UDP را در هر حالت تست کنید؛ روش/کلید اشتباه و تلاش plaintext برای کاربر رمزنگاری‌شده باید رد شوند. تغییر رمزنگاری A نباید B را قطع کند. ویرایش نام یا سهمیهٔ A نباید کلید رمزنگاری آن را عوض کند. overhead رمزنگاری نباید به مصرف payload اضافه شود.

در اطلاعات اتصال، «کپی لینک اتصال» باید قالب زیر را بدهد و IP/کلید همان کاربر را داشته باشد:

```text
pingtunnel://SERVER_IP_OR_DOMAIN?lport=1080&mode=vpn&key=USER_NUMERIC_KEY
```

پشتیبانی import لینک را در اپ واقعی تست کنید. این URI فیلد رمزنگاری ندارد؛ برای کاربران رمزنگاری‌شده روش و کلید را جدا تنظیم کنید یا از دستور کامل پنل استفاده کنید. گزینهٔ Zstandard را در تست جدا روشن کنید؛ مصرف باید بر حسب دادهٔ بازشده حساب شود.

## تفکیک و کنترل

- با A دانلود کنید؛ مصرف B نباید افزایش یابد. روی هر دو اتصال موازی بسازید.
- حجم کوچک برای A تنظیم کنید. بعد از رسیدن مجموع آپلود + دانلود به سقف، ادامهٔ ترافیک A باید متوقف شود، ولی B ادامه بدهد.
- A را غیرفعال، منقضی یا حذف کنید؛ نشست‌های آن باید قطع شوند. B نباید reconnect لازم داشته باشد.
- یک نشست B را باز نگه دارید و هم‌زمان کاربران دیگر را ویرایش یا اطلاعات ورود پنل را عوض کنید؛ نشست B نباید restart هسته ببیند.
- outbound را برای A روی SOCKS5 و سپس HTTP بگذارید. IP خروجی مقصد باید متعلق به پروکسی باشد. HTTP همراه UDP باید رد شود، نه از IP سرور مستقیم خارج شود.
- پس از stop/start عادی، مقدار مصرف باید دقیقاً حفظ شود. تست kill -9 را فقط روی VPS آزمایشی انجام دهید؛ مصرف ممکن است تا حدود ۲۵۶ KiB برای هر کاربر افزایش محافظه‌کارانه داشته باشد و نباید کاهش یابد.

## مقایسهٔ سرعت

روی **همان VPS، همان کلاینت، همان مقصد، همان ساعت و همان مسیر**، PingTunnel اصلی و namedICMP را پشت‌سرهم با یک کلاینت آزمایش کنید؛ سرویس‌ها نباید هم‌زمان روی همان IP فعال باشند. برای هر سرویس پنج بار تست را تکرار کنید و میانه را مقایسه کنید.

ثبت کنید: throughput آپلود و دانلود، latency، packet loss، CPU درصدی، RSS، تعداد نشست، فایل‌سیستم state، تعداد کاربران و پارامترهای TCP کلاینت. مقدار `CPU: 13min` در systemd زمان تجمعی CPU است و درصد مصرف لحظه‌ای نیست.

```bash
systemctl show namedicmp -p MainPID -p CPUUsageNSec -p MemoryCurrent
top -p "$(systemctl show namedicmp -p MainPID --value)"
journalctl -u namedicmp --since '10 minutes ago' --no-pager
```

بار ۱، ۱۰ و ۳۰ اتصال موازی را حداقل ۱۵ دقیقه ادامه دهید. هر افت سرعت را با دادهٔ مسیر شبکه و لاگ همراه کنید. کاهش سرعت یا افزایش حافظهٔ پیوسته به معنای قبول نشدن این نسخه است؛ صرف سبز بودن تست‌های Go معیار انتشار نهایی نیست. CPU یا RAM نباید با تعداد بازشدن صفحهٔ پنل رشد پیوسته داشته باشد.

اگر ابزار `tc netem` در محیط آزمایشی دارید، loss و reorder را روی رابط آزمایش محدود اعمال کنید؛ این تغییر را روی رابط SSH سرور اصلی انجام ندهید. TCP باید دادهٔ صحیح تحویل دهد و مصرف ارسال مجدد دوباره محاسبه نشود.

## نتیجهٔ فعلی

در محیط ساخت: ایراد چند مقصد UDP، datagram بزرگ و ID مشترک TCP/UDP روی نسخهٔ 0.1 بازتولید و با اصلاح هسته رفع شدند. تست‌های انتقال TCP/UDP با هر چهار حالت رمزنگاری، golden vector مستقل AEAD، حفظ تنظیمات قدیمی، افت پنجره و retransmit، تفکیک کاربران و سهمیه، ذخیره‌سازی، SOCKS5 TCP/UDP و ادامه پس از datagram خراب، HTTP buffered data، CSRF و DOM پنل اجرا می‌شوند. transport تست **سوکت خام ICMP نیست**.

raw ICMP، Unix management socket، systemd نصب‌شده، دریافت گواهی واقعی، اپ موبایل و سرعت WAN در این محیط تأیید نشده‌اند. تا ثبت نتیجهٔ این مراحل، عنوان پروژه آلفا باقی می‌ماند.
